findaro documentation

findaro is AI search for product catalogs. You send a catalog, call one search endpoint (or add the <findaro-search> widget), and shoppers can search in their own words, including Indian English and Hinglish.

Quickstart →Keys, import a catalog, search, add the widget. About 5 minutes. Widget →Attributes, events, theming and custom product cards. SDK →Headless TypeScript client: search, streaming chat, patches. API reference →Every endpoint and schema, generated from the OpenAPI spec.

Concepts

Projects and keys

A project is one catalog plus its settings. Each project has two keys:

  • Admin key (fdr_admin_…): imports and deletes documents, reads and overrides the schema, changes settings. Server-side only: requests from a browser (with an Origin header) are refused.
  • Search key (fdr_search_…): read-only, can only call /v1/search and /v1/chat. Safe to put in a web page. Browser requests are accepted only from the project's allowed_origins.

Send either key as Authorization: Bearer <key> (or X-Findaro-Key: <key>).

Catalog and schema

Import JSON, JSONL or CSV (up to 50 MB per file), or push up to 10,000 documents per request as JSON. Imports run as background jobs. On the first import findaro infers a role for every field (title, description, price, facet, category, image URL…). You can review the inferred schema and override any field; overrides are applied by a background reindex while search keeps working.

Query understanding

Before retrieval, the query is turned into a plan built only from your project's own fields and values: price ranges (“under 500”, “500 ke andar”, “1.5k”), quantities (“5 L” is never a price), attribute values such as colours, materials, sizes and brands, categories, and cheap/premium intent. Hinglish words are translated by language packs. What was applied comes back in understood.chips; each chip carries a remove patch so your UI can undo it.

A small LLM planner is used only when the rules can't account for some words. It runs behind a timeout with the rules plan as fallback, is cached, and is never called for search-as-you-type requests ("llm": false).

Retrieval

Hybrid: BM25 keyword search (typo-tolerant, with transliteration so Devanagari matches romanised Hindi) plus multilingual semantic vectors, fused with Reciprocal Rank Fusion. Every response reports match_quality (good, weak or none), any filters that were relaxed to find results, and which results are close rather than exact matches.

Chat

POST /v1/chat streams Server-Sent Events: conversational refinement (“cheaper”, “only black”, “not slippers”), questions about the products on screen, and questions about one product (product_ids). Answers are grounded: the model sees only the products on screen, numbers are filled in from your data, and every sentence is checked before it streams. General know-how is sent separately as part: "general" so you can label it.

Hosted or self-hosted

The API is the same either way. On the hosted beta we give you an API URL (__API_URL__), a project id and both keys. To self-host, run the open-source stack with docker compose and create projects yourself: see Self-hosting.

Limits worth knowing

  • Search requests are rate limited per key (50 requests per second by default on self-hosted installs).
  • Results are cached for 60 seconds per data version; send Cache-Control: no-cache to bypass.
  • Chat sessions last 30 minutes.
  • size is at most 100 results per page.

Not built yet: autocomplete, analytics, recommendations, personalization, connectors and a dashboard.
